## 修复 GitHub Actions 构建失败（CVE 导致依赖审计阻断）

用户报「github 构建失败了」。根因不是代码问题，而是**新增披露的两个 HIGH 漏洞让安全门禁失败**。

### 故障链
- `CI and container images` 失败：`Repository security scan`（Trivy）+ `npm run audit:prod` 均报 6 处 HIGH，退出码 1。
- `Build and push Aliyun ACR images` 失败：它不是独立故障，而是 `Verify this commit passed required CI` 门禁等到 CI 红了就退出。**CI 修好它自动恢复，不用单独处理。**

### 漏洞与修复
| 包 | 漏洞 | 原版本 → 修复版本 | 来源 |
|---|---|---|---|
| joi | CVE-2026-118772（正则 ReDoS） | 18.2.9 → 18.3.1 | core-api / exam-api 直接依赖 |
| follow-redirects | CVE-2026-116689（跨域重定向信息泄露） | 1.16.1 → 1.16.2 | axios（core-api/core-admin/notification-service）、http-proxy（platform-api）传递依赖 |

### 操作要点（下次照做）
1. 直接改 `package.json`（core-api、exam-api 的 `joi` 改为 `^18.3.1`），再 `npm install --package-lock-only`。diff 只有 4 行，很干净。
2. 传递依赖**不要用 `npm audit fix`**：它会把 @babel 整棵树顺带升级（实测 816 行 diff）。正确做法是 `npm update follow-redirects --package-lock-only`，只动 3 行。
3. 本地 `node_modules` 可能不跟随 lock 更新（npm 报 "up to date" 但版本还是旧的，因为 `node_modules/.package-lock.json` 与实际目录不同步）。删掉该包目录再 `npm install` 即可。
4. **本机 `npm ci` 在 Windows 会失败**：npm 的 safe-delete 走回收站失败（`Error during a 'trash' operation`）。验证 lock 同步用 `npm ci --dry-run --omit=dev`，实际安装用 `npm install`。CI 在 Ubuntu 上用 npm ci 不受影响。
5. 验证口径：`npm run audit:prod` + `npm run check`（全量 20 项）+ 各受影响项目单跑（check:core 135 / check:exam 56 / check:gateway 58 / check:notification 39 / check:admins / check:supply-chain）。
6. Trivy 扫的是所有 lock，用一段 node 脚本遍历 12 个工作区的 lock 里 `follow-redirects !== 1.16.2` 和 `joi 18.x < 18.3`，确认无残留。

### 结果
commit `baae9c9`，7 个文件 / 22 行改动。CI 4m16s success，ACR 8m6s success。

## 六、GitHub 构建失败排查与修复（晚间）
